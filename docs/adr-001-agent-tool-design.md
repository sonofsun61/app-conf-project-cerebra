# ADR 001: Дизайн первого Tool и конфигурация LLM

**Статус:** Принято  
**Дата:** 21.09.2026  
**Команда:** Cerebra (Волов, Тарнов, Черевко) 
**Проект:** app-conf-project-cerebra

## Контекст

В рамках практики требовалось реализовать первый Tool для AI-слоя проекта, подключить его к CrewAI и обеспечить переключаемую конфигурацию LLM через `pydantic-settings`.

Для проекта был выбран Tool `check_commit_safety`. Его задача - проверять файлы проекта перед Git-коммитом и сообщать о потенциально небезопасных или нежелательных для публикации данных.

Tool проверяет:

- потенциальные секреты и чувствительные файлы;
- нежелательные файлы и каталоги;
- слишком большие файлы;
- незавершённые merge-конфликты.

Инструмент работает только на чтение: он не удаляет, не изменяет и не добавляет файлы в Git.

Конфигурация AI-слоя должна поддерживать локальный запуск через Ollama и возможность переключения провайдера через `.env`. При этом `.env` не должен попадать в Git, а API-ключ хранится как `SecretStr`.

## Рассмотренные варианты

### 1. Конфигурация через `os.getenv`

Плюсы:

- минимальное количество кода;
- не требуется отдельная модель настроек.

Минусы:

- нет автоматической проверки допустимых значений;
- сложнее контролировать типы;
- выше риск поздно обнаружить ошибку в имени провайдера или параметрах;
- секреты приходится обрабатывать вручную.

### 2. Конфигурация через `pydantic-settings`

Плюсы:

- типизированные настройки;
- валидация `LLM_PROVIDER` через `Literal`;
- безопасное хранение API-ключа через `SecretStr`;
- поддержка общего `.env` благодаря `extra="ignore"`;
- единая точка доступа к настройкам.

Минусы:

- дополнительная зависимость;
- конфигурация становится немного сложнее простой работы с `os.getenv`.

### 3. Ошибки Tool через исключения

Плюсы:

- стандартный механизм Python;
- удобно для внутренних ошибок приложения.

Минусы:

- необработанное исключение может остановить работу агента;
- LLM получает технический traceback вместо понятного описания;
- модель не понимает, как исправить следующий вызов.

### 4. Безопасный возврат ошибки через JSON

Плюсы:

- агент продолжает работу после некорректного вызова;
- сообщение можно сформулировать так, чтобы модель понимала причину ошибки;
- формат ответа одинаков для успешного и ошибочного сценария.

Минусы:

- необходимо явно обрабатывать ожидаемые ошибки;
- вызывающая сторона должна различать `status="error"` и успешный результат с `safe_to_commit=false`.

### 5. Локальные модели Ollama

Изначально использовалась `qwen2.5-coder:7b`, указанная в руководстве практики. Модель корректно определяла необходимость использования `check_commit_safety` и формировала имя Tool и аргументы, но возвращала вызов как обычный JSON-текст в `content`. Из-за этого CrewAI воспринимал его как финальный ответ и Tool фактически не выполнялся.

После проверки была выбрана `qwen3:4b-instruct`. С этой моделью CrewAI корректно получает native tool call и реально выполняет `check_commit_safety`.

## Решение

Для конфигурации AI-слоя используется `pydantic-settings`.

Рабочие значения провайдера и модели задаются через `.env`, а `ai/config.py` содержит типизированные значения по умолчанию. `.env.example` содержит пример рабочей конфигурации без секретов.

Локальная модель по умолчанию - `qwen3:4b-instruct` через Ollama.

Создание LLM вынесено в единственную функцию `get_llm()` в `ai/llm_factory.py`.

Tool `check_commit_safety` принимает:

- `scope`: `staged` или `all_tracked`;
- `max_file_size_kb`: целое число от 1 до 10240.

При `scope="staged"` анализируется содержимое, которое реально находится в Git index.

Tool всегда возвращает JSON-строку.

Успешная проверка имеет вид:

```json
{
  "status": "ok",
  "safe_to_commit": true,
  "checked_files": 1,
  "issues_count": 0,
  "issues": []
}
```

Если Tool успешно обнаружил проблему проекта, `status` остаётся `"ok"`, но `safe_to_commit` становится `false`.

Ошибки самого вызова возвращаются в виде:

```json
{
  "status": "error",
  "message": "..."
}
```

Необработанные исключения наружу не должны выходить.

Значения найденных секретов не включаются в результат Tool: возвращаются только тип проблемы, путь к файлу, номер строки и безопасное описание.

## Последствия

Преимущества принятого решения:

- Tool можно использовать перед реальным Git-коммитом;
- ошибки входных параметров не останавливают агента;
- формат результата понятен и разработчику, и LLM;
- `safe_to_commit=false` отделён от ошибки самого Tool;
- секреты не должны попадать в ответ инструмента;
- конфигурация LLM централизована;
- локальная модель позволяет выполнять практику без облачного API.

Ограничения:

- поиск секретов основан на наборе шаблонов и не гарантирует обнаружение всех возможных секретов;
- возможны ложные срабатывания;
- проверка нежелательных файлов зависит от заданного списка правил;
- `qwen3:4b-instruct` была выбрана вместо модели из исходного руководства из-за различий в поддержке native tool calling;
- LLM может добавлять интерпретации, которых нет непосредственно в JSON Tool, поэтому для критичных сценариев ответ агента следует ограничивать данными инструмента.

## Наблюдения из трассы

### `run-01.log` - корректный вызов

Агент один раз вызвал `check_commit_safety` с аргументами:

- `scope="staged"`;
- `max_file_size_kb=1024`.

Tool вернул:

- `status="ok"`;
- `safe_to_commit=true`;
- `checked_files=0`;
- `issues_count=0`.

Агент сформировал финальный ответ на основании результата Tool. Повторный вызов не потребовался.

### `run-02.log` - недопустимый `scope`

Tool был вызван с:

- `scope="full"`;
- `max_file_size_kb=1024`.

Инструмент не выбросил исключение и вернул:

- `status="error"`;
- сообщение о том, что допустимы только `staged` и `all_tracked`.

Агент корректно объяснил пользователю причину ошибки.

### `run-03.log` - недопустимый размер

Tool был вызван с:

- `scope="staged"`;
- `max_file_size_kb=0`.

Инструмент вернул контролируемую ошибку с допустимым диапазоном от 1 до 10240. Traceback не возник.

### `run-04.log` - реальная проблема в staging

В staging был принудительно добавлен тестовый файл `test-debug.log`.

Tool успешно выполнил проверку и вернул:

- `status="ok"`;
- `safe_to_commit=false`;
- `checked_files=1`;
- `issues_count=1`;
- проблему типа `unwanted_file`.

Этот сценарий подтвердил различие между ошибкой вызова Tool и успешно обнаруженной проблемой проекта.

Также было замечено, что модель может добавлять небольшие пояснения, которых нет непосредственно в Output Tool. Поэтому для подобных проверок в задаче агента явно указывается требование основывать вывод только на результате инструмента.

### Поведение локальных моделей

`qwen2.5-coder:7b` через Ollama определяла нужный Tool и формировала корректные аргументы, но возвращала описание вызова как текст вместо native tool call.

`qwen3:4b-instruct` корректно выполнила native tool calling, после чего в трассе появились `Tool Execution Started`, `Tool Execution Completed` и финальный ответ на основании результата Tool.

## Когда пересмотреть

Решение следует пересмотреть, если:

- CrewAI изменит API объявления или вызова Tools;
- будет заменён LLM-провайдер или локальная модель;
- количество проверок `check_commit_safety` существенно вырастет;
- появится требование автоматически исправлять найденные проблемы;
- потребуется более надёжное обнаружение секретов специализированным сканером;
- Tool начнёт работать с удалёнными репозиториями или CI;
- появятся требования к производительности при проверке больших репозиториев.
